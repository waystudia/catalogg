# WayYaam: меню, доступ и реальные тестовые заказы — 30.10.2026

Оптимизация установлена в PostgreSQL на `api.wayyaam.ru`. Интерфейс использует один RPC меню; итоговый статический релиз и подтверждение CI фиксируются отдельно после публикации. Исходный рабочий каталог с несвязанными изменениями сохранён. Ветка реализации `codex/catalog-performance-orders-20261030`, отдельный managed worktree; база содержит пользовательский релиз `72b47343` с компактной корзиной. `origin/main` на момент подготовки — `fafd2ca0`.

## Что изменилось

- Повторные проверки членства и видимости каталогов вынесены в вычисляемые один раз массивы в RLS. Предикаты доступа сохранены, `WITH CHECK` не ослаблен. До установки сравнивались доступные строки 34 акторов (включая анонимного) по 10 таблицам: различий нет.
- `get_catalog_menu_snapshot` возвращает каталог, товары, категории, изображения, теги, ресурсы, тему, настройки разделов, модификаторы и расположение одним API-вызовом. Обычные таблицы остаются защищены RLS. Для старого API допускается возврат к прежним запросам только при `PGRST202`; ошибки доступа не маскируются.
- Серверный кеш анонимного меню живёт 30 секунд. Изменения 11 таблиц немедленно сбрасывают соответствующий кеш. Перед каждым чтением повторно проверяется доступность самого каталога. Сборщик принадлежит отдельной роли `NOLOGIN NOBYPASSRLS`, наследующей только анонимный доступ; приватная таблица недоступна клиентам. Авторизованные пользователи читают через собственный RLS, общий кеш обходят. Цена, скрытие публикации, неизвестный и тестовый каталог проверены транзакционным интеграционным тестом с откатом изменений.
- Вкладка дополнительно объединяет совпадающие загрузки и хранит до 32 публичных меню в памяти на 15 секунд. При смене авторизации, собственных правках и событиях Realtime кеш очищается. Данные не записываются в Service Worker или постоянное хранилище. Имеющийся кеш TanStack Query сохранён.
- Браузер на `wayyaam.ru`/`www.wayyaam.ru` использует уже существующий `/api`-прокси к тому же Kong/Supabase: отдельный домен API иногда зависал при свежем Chromium-сеансе. Проверены одинаковые ответы прямого API и прокси. Другие окружения и Supabase-проекты сохраняют настроенный URL; TLS/Caddy не менялись. Это дополнительное улучшение сетевого пути, приведённые нагрузочные цифры получены на прямом API до этого переключения.
- У старого Mangal отдельные таблицы: они сохранены, три чтения настроек разделов объединены. Основной RPC применяется к платформенным каталогам; локальные шаблоны по-прежнему могут загружаться локально.
- Исправлена блокировка допустимых тестовых заказов проверкой активации. Сохранены отдельная проверка тестового контура и проверка активации настоящих ресторанов.
- Исправлена неоднозначная переменная `account_id` в `confirm_client_order_receipt`. Проверки телефона, сессии и этапов заказа сохранены.
- Внешние web push для тестовых заказов подавлены; внутренние записи истории сохраняются.

## Публичное меню: одинаковые каталоги и транспорт

Finik, Barakat, Rizih; HTTP/1.1 keep-alive, до 256 соединений, 15 секунд на ступень, пауза посетителя 1 секунда. «До» — 13 отдельных запросов уже после оптимизации RLS; «после» — один RPC с серверным кешем. Это сравнение способа загрузки меню, а не прежнего HTTP-теста главной страницы. P95 сценария включает очередь генератора и весь набор запросов. RPS отдельных запросов напрямую сравнивать нельзя: размер набора разный.

|---:|---:|---:|---:|---:|
| 100 | 8,29 с | 0,67 с | 2/4095 | 0/1346 |
| 200 | 11,98 с | 1,10 с | 1/5564 | 2/2288 |
| 300 | 15,00 с | 3,05 с | 133/6877 | 6/2336 |

Ошибки здесь — сетевые таймауты/прерывания, HTTP 5xx не получены. Редкие сетевые сбои остаются; нулевую долю ошибок на 300 обещать нельзя. На 300 CPU в обоих вариантах близок к 100%, но новый вариант успевает выполнить существенно больше полных чтений меню. «9,08 с» из предыдущего отчёта относилось к P95 отдельного API-запроса при 200 синтетических одновременных сценариях, а не к полной загрузке экрана для 200 людей.

## Заказы: 300 клиентов, отдельный ресторан, 5 водителей

Созданы настоящие записи Auth и клиентские сессии для 300 тестовых клиентов, отдельный тестовый ресторан с десятью блюдами и 5 тестовых водителей. Адреса почты `.invalid`, телефоны синтетические; SMS/письма не отправлялись. Ресторан скрыт от обычных анонимных посетителей. Доставка ограничена своими пятью тестовыми курьерами, переход к настоящим платформенным водителям отключён. Все участники, заказы, доставки, начисления и комиссии помечены тестовыми.

Каждый клиент читает меню и создаёт заказ через обычный защищённый RPC. Ресторан проходит принятие, готовку, готовность и назначение доставки; водитель принимает доставку, приезжает, проходит кассовые подтверждения и проверку QR, получает заказ, отмечает путь/прибытие/передачу; клиент подтверждает получение; водитель закрывает доставку. Финальный статус читается через обычный API. Водитель обрабатывает одну доставку одновременно, ресторан — до трёх действий одновременно. Подмена финальных статусов прямым SQL не использовалась.

Это симуляция действий через настоящий API, без физической готовки, поездки и денежных переводов. Полный цикл включает очередь к пяти водителям и несколько последовательных операций; его нельзя считать временем HTTP-ответа или обещанием реальной доставки. Все клиенты стартуют одновременно, однако транспорт ограничен 128 сокетами: у 300 P95 ожидания сокета генератора 1,90 с. Облачный или иной генератор даст другие абсолютные задержки.

На основных ступенях завершены 935 заказов. Первая попытка 75 завершила 74: один клиент получил таймаут меню до создания заказа. Добавлены ограниченные повторы чтения, создание с тем же idempotency key и проверка фактического состояния после неопределённого результата записи. После исправления 75/75; при 200 один транспортный сбой восстановлен без дубля. Повтор записи возможен только после сверки состояния, произвольного повторения платёжных/курьерских действий нет. Отрицательные проверки намеренно получают отказ: чужой водитель, неправильный клиент и преждевременное завершение. Проверяется точная причина отказа. Повтор создания возвращает тот же order ID.

После последней миграции дополнительно прошёл полный цикл 10/10. С учётом повторов и отладки: 1022 заказа завершены, 1022 доставки закрыты; один первоначальный диагностический заказ отменён через API. Все 2044 связанные записи биллинга тестовые; дублей idempotency key нет. Настоящих заказов в базе 27 (до тестовых фикстур их также было 27; общий исходный счёт включал ещё 12 старых тестовых). Пять тестовых водителей переведены офлайн через API, 300 тестовых клиентских сессий завершены. Тестовые аккаунты и история оставлены для воспроизводимости; учётные данные хранятся в приватном файле, в Git не включены.

## Что нагружает сервер

VPS: 2 vCPU, 3915 MiB RAM. На ступени 300 заказов CPU в среднем 72,2%, на пиках 100%; PostgreSQL в среднем около 41,2% общей мощности двух ядер, Kong 6,2%, PostgREST 5,6%. Свободной RAM оставалось минимум 1756 MiB. Это насыщение процессора на пиках, а не 100% занятая оперативная память. По всем ступеням RAM оставалась доступной. После чистки на диске 13 GiB свободно из 38 GiB (68% занято).

Наибольшие суммарные расходы SQL за окно измерений: сборка меню (совместно анонимные и авторизованные вызовы), обработка Realtime WAL, создание заказов, затем отдельные чтения изображений/тем/товаров. `pg_stat_statements` агрегирован по query ID с суммированием разных ролей; это время выполнения, включающее ожидания, а не точное CPU-время каждой функции. Накопленные показатели не сбрасывались. Замеры контейнеров нормированы на два ядра (Docker 100% одного ядра = 50% хоста).

Гарантия «300 настоящих пользователей в браузере без задержек» из этого теста не следует. Изображения, рендеринг на телефонах, нестабильная мобильная сеть, реальные интервалы готовки и движение курьеров не имитировались. При открытии авторизованного меню общий публичный кеш намеренно не используется. Дальнейшие цели при росте: стоимость авторизованной сборки меню, Realtime и создания заказа; насыщение двух CPU и внешние сетевые таймауты остаются ограничениями. Очередь в генераторе моделирует занятость пяти водителей; это не новая серверная очередь фоновых задач.

## Воспроизведение и проверки

- `scripts/verify-menu-access.py <migration>` — сравнение RLS до/после внутри откатываемой транзакции. Исторический результат 34×10 получен до установки первой миграции; повтор после установки уже не доказывает первоначальное сравнение.
- `scripts/verify-public-menu-cache.py <cache-migration>` — установка миграции и проверки в транзакции с откатом. Запускать до установки соответствующей миграции, в изолированной базе или адаптировать к уже установленной схеме.
- На VPS: `python3 scripts/provision-order-load-fixture.py --clients 300 --apply`. Скрипт требует окружения Docker Supabase на VPS, вывод содержит секреты: направлять в файл 0600, не в терминальные/CI-логи. Повтор продлевает только собственные тестовые сессии и включает только своих тестовых водителей.
- Из локального окружения с `.env.local`: `node scripts/load-test-order-lifecycle.mjs --fixture /private/fixture.json --output output/orders.jsonl --levels 10,20,30,50,75,100,150,200,300 --controls true`. JWT действует 15 минут, клиентская сессия — 2 часа; перед долгим новым прогоном повторить provision. После теста выключить своих водителей через API и завершить собственные тестовые сессии.
- `node scripts/load-test-wayyaam.mjs --duration 15 --levels 100,200,300 --slugs finik,barakat,rizih --snapshot true --output output/public.jsonl`. `--snapshot false` использует прежние отдельные чтения. Нельзя запускать два сравниваемых генератора одновременно.
- `scripts/monitor-wayyaam-resources.py` запускается на VPS, читает `/proc`, cgroups и статистику PostgreSQL. Перед повтором выбрать новое имя `--stop-file`; существующий stop-файл немедленно завершает сбор. Не сбрасывает системные счётчики.

Перед изменениями сохранён полный дамп `/opt/supabase-backups/pre-menu-load-20261030.dump`; три SQL-миграции применены атомарно через `psql -1`. На этом self-hosted экземпляре нет таблицы истории Supabase CLI, облачный `db push` не использовался. Старые статические релизы, общий архив хешированных ассетов и резервные копии сохраняются. Caddy и стек Supabase не перезапускаются для статического выпуска.

Локально: 390 Node-тестов + 189 unit, 91 browser-тест, lint (0 ошибок, 3 существующих предупреждения), typecheck, production build с `VITE_BASE_PATH=/`, guard-тесты PWA/TLS/static release, `git diff --check`. Сводные измерения без токенов: [JSON](2026-10-30-menu-orders-results.json). Приватные фикстуры и полные технические логи в Git не включены.
