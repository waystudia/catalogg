# ТЗ: привязка водителя к ресторанам

## Проблема

Сейчас редактор водителя постоянно показывает полный список ресторанов. Этот список выглядит как список уже подключённых ресторанов, занимает большую часть мобильного экрана и не позволяет суперадминистратору выбрать финансовый тип связи. При сохранении экран пересоздаёт строки `restaurant_couriers` без `courier_type`, поэтому тип, выбранный рестораном, может быть потерян.

## Цель

Сделать один согласованный сценарий управления связью «водитель — ресторан» из кабинета суперадминистратора и из настроек ресторана. Оба кабинета читают и меняют одну строку `restaurant_couriers`.

## Экран суперадминистратора

1. Раздел называется «Рестораны и условия работы».
2. По умолчанию показываются только уже подключённые рестораны.
3. Поле «Найти ресторан» ищет по названию без учёта регистра и лишних пробелов.
4. Неподключённый ресторан появляется в результатах поиска с кнопкой «Подключить».
5. После подключения открывается карточка связи с обязательным выбором:
   - «Штатный с зарплатой» (`staff_salaried`);
   - «Штатный без зарплаты» (`independent`, действующая финансовая модель самостоятельного водителя без зарплаты ресторана).
6. В каждой карточке отдельно меняется признак «Основной курьер». Один водитель может быть основным у нескольких ресторанов. В одном ресторане основным остаётся только один водитель.
7. Связь можно удалить до сохранения. Удаление переводит её в неактивное состояние, но не стирает историю.
8. Кнопка «Сохранить» недоступна, пока хотя бы у одной новой/активной связи не выбран тип.

## Экран ресторана

1. В «Настройки ресторана → Доставка и заказы → Курьеры и платформа» ресторан видит тот же тип связи.
2. Тип разрешено менять и у уже классифицированного курьера, а не только у старой записи без типа.
3. После сохранения и повторной загрузки изменение, сделанное рестораном, видно суперадминистратору, и наоборот.
4. Под типом показывается действующее правило комиссии, чтобы переименование не скрывало финансовый смысл.

## Данные и безопасность

1. Источник истины — `public.restaurant_couriers` (`restaurant_id`, `driver_id`, `is_active`, `is_primary`, `priority`, `courier_type`).
2. Суперадминистратор сохраняет весь набор связей через одну транзакционную RPC-функцию `save_driver_restaurant_assignments`.
3. RPC доступна только авторизованному `platform_admin`, проверяет существование водителя и ресторанов, отклоняет неизвестный тип и дубли ресторанов.
4. При назначении нового основного курьера прежний основной курьер этого ресторана автоматически перестаёт быть основным.
5. Существующие правила распределения заказов, комиссий и бесплатной доставки не меняются.

## Мобильный UX и критерии приёмки

1. Ширина страницы не превышает viewport на 319 px; горизонтального скролла нет.
2. Интерактивные элементы имеют высоту не менее 44 px.
3. Полный каталог ресторанов не рендерится до ввода поиска.
4. Поиск находит ресторан по фрагменту названия.
5. Сохранение без выбранного типа невозможно.
6. Смена типа из суперадмина отображается в кабинете ресторана после обновления запроса; обратное направление работает аналогично.
7. Для текущих привязок не теряются `courier_type`, `is_primary` и `priority`.
