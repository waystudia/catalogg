# Plan: Restaurant legal activation MVP

**Branch**: `codex/restaurant-legal-activation-mvp-20260805`
**Backup branch**: `codex/backup-before-restaurant-activation-20260805`
**Status**: Implemented locally — awaiting user review and explicit commit approval

## Goal

Уполномоченный представитель ресторана отдельно принимает актуальный пакет документов и подтверждает действие одноразовым кодом, после чего сервер атомарно фиксирует неизменяемый акцепт и только тогда разрешает публикацию и реальные заказы.

## Repository audit

- Приложение использует React 18, TypeScript, Vite, HashRouter и Supabase Auth/Postgres/RLS/RPC/Edge Functions.
- Ресторанный кабинет открывается по `/:slug/dashboard`; единый вход получает маршрут через `resolve_current_login_redirect()`.
- Владелец связан с рестораном через `clients.owner_user_id` и `catalog_members`; роли сейчас ограничены `owner/admin/editor/viewer` и не имеют отдельного права на юридический акцепт.
- Публичный каталог отбирает `catalogs.status = 'published'`, но прямой публичный RPC создания заказа проверяет только существование `catalog_id`.
- Текущее первое согласие использует `clients.consent_given` и `mark_client_personal_data_consent()`; OTP, пакет версий, снимки, idempotent acceptance и отдельные обязательные подтверждения отсутствуют.
- `legal_consent_records` уже хранит отдельные версии/хеши отдельных согласий, но не является записью акцепта ресторанного пакета и закрыт для обычного чтения.
- Комиссия ресторана сейчас вычисляется в клиентском коде по заказам; тестовые заказы и юридический статус не представлены в модели заказа.
- Существующие HTML-документы имеют редакцию 1.0, но ресторанная оферта содержит незаполненный тарифный placeholder и не может автоматически считаться опубликованным договором.
- Локальная ветка `main` совпадала с `origin/main` на `442d5caf`; рабочее дерево до начала было чистым.
- Базовый gate зелёный: 341 node-тест, 158 unit-тестов, 42 browser-теста, lint, typecheck, production build и `git diff --check`.

## Parent split

Полное ТЗ разбито на независимо проверяемые пользовательские возможности:

1. Супер-админ переводит ресторан в ожидание, а уполномоченный владелец принимает фиксированный пакет документов ручным одноразовым кодом; только после этого сервер разрешает публикацию и реальные заказы.
2. Супер-админ создаёт, хеширует, публикует и архивирует неизменяемые версии документов и пакетов, а ресторан открывает/скачивает каждую принятую редакцию.
3. Супер-админ и владелец видят журнал доказательств и скачивают визуально проверенное PDF-подтверждение акцепта.
4. Супер-админ включает демонстрационный режим, в котором тестовые заказы помечены и исключены из публикации, оплаты, водителей, чеков, комиссий и финансов.
5. Ресторан повторно принимает только существенную новую редакцию с grace period и серверным ограничением новых заказов после срока.
6. Владелец отправляет запрос исправления данных, а обе стороны получают внутренние уведомления и безопасные шаблоны для ручной отправки.
7. Расширенные email/SMS-уведомления и автоматическое заполнение реквизитов подключаются после отдельного выбора провайдеров.

Этот план реализует только пункт 1 как первый walking skeleton. Последующие пункты остаются обязательными срезами полного MVP из ТЗ.

## Slice 1: Владелец активирует ожидающий ресторан ручным одноразовым кодом

**Actor**: супер-администратор и уполномоченный представитель ресторана.

**Trigger**: супер-администратор завершает настройку ресторана; представитель входит, отдельно подтверждает обязательные условия, запрашивает и вводит ручной одноразовый код.

**Observable outcome**: появляется append-only запись акцепта с версиями, хешами и снимками; ресторан становится `active`, появляется в клиентском каталоге и принимает реальный заказ. До этого публичная выдача и серверный RPC заказа отказаны.

**Production path**: раздел супер-админа → расширяющая миграция и защищённые RPC → единый login redirect → `/restaurant/activation` → пакет документов и отдельные checkbox → хешированный OTP → атомарный акцепт/аудит/статус → публичный каталог и существующие order RPC.

**Release constraint**: скрыто/заблокировано до публикации юридически проверенного пакета документов; миграция не применяется к production до подтверждённого backup.

### Acceptance criteria

- [ ] Новые ресторанные клиенты создаются с отдельным юридическим статусом `draft`, неопубликованным каталогом и выключенным приёмом реальных заказов.
- [ ] Супер-администратор видит ресторан в изолированном разделе «Договоры и активации» и может перевести только подготовленный ресторан в `awaiting_acceptance`.
- [ ] Завершение настройки невозможно без владельца/представителя, номера подтверждения, тарифа и опубликованного полного пакета обязательных документов; сервер возвращает точный список отсутствующих условий.
- [ ] Все существующие рестораны получают `legacy_review_required`, перестают считаться опубликованными/допущенными к новым реальным заказам и проходят тот же путь: проверка настройки супер-администратором → `awaiting_acceptance` → личный акцепт представителем → `active`; автоматической активации и legacy-bypass нет.
- [ ] `resolve_current_login_redirect()` направляет участника ожидающего ресторана на `/restaurant/activation`; обычный кабинет не монтируется до активации.
- [ ] На странице активации видны реальные реквизиты ресторана, представитель, тариф, комиссия, доставка и актуальные версии документов; пустые данные остаются пустыми, а не заполняются вымышленными значениями.
- [ ] Каждый обязательный checkbox независим, изначально выключен и передаётся на сервер как полный набор версионированных утверждений; маркетинговые согласия независимы и необязательны.
- [ ] Только `owner` или участник с серверным `can_accept_legal_documents = true` может запросить код и принять пакет своего ресторана; подмена `restaurant_id`/`catalog_id` не влияет на серверный выбор субъекта.
- [ ] Ручной код содержит 6 цифр, показывается супер-администратору только при создании, хранится только как SHA-256/HMAC-хеш, живёт 10 минут, имеет максимум 5 попыток, cooldown повторной выдачи 60 секунд и не может использоваться повторно.
- [ ] Код нельзя запросить, пока сервер не получил полный набор обязательных checkbox и идентификатор неизменившегося опубликованного пакета документов.
- [ ] Успешное подтверждение выполняется одной транзакцией: блокирует код, повторно проверяет пользователя/право/статус/пакет, создаёт один append-only акцепт со снимками, пишет аудит, переводит ресторан в `active` и публикует каталог.
- [ ] Повтор той же команды после сетевой ошибки возвращает существующий действующий акцепт и не создаёт второй; неправильный, истёкший или исчерпанный код не меняет статус.
- [ ] Акцепт сохраняет пользователя, представителя, основание полномочий, замаскированный destination, метод `manual_code`, время, session id, IP/user-agent metadata, checkbox JSON, opened-documents JSON, restaurant/tariff snapshots, версии/хеши документов и итоговый acceptance hash.
- [ ] Обычный пользователь не может читать чужой профиль/код/акцепт, ресторан не может обновлять или удалять акцепт, а супер-админ не может вызвать ресторанный RPC акцепта за владельца.
- [ ] Публичный каталог, оба существующих restaurant order RPC и fallback `create_public_order` разрешают реальный заказ только для `active`; отказ происходит до вставки заказа и списания остатков, включая все ранее созданные рестораны до их активации.
- [ ] Код заказа, WhatsApp status link, idempotency fallback, доставка, карты, PWA session и текущая супер-админка сохраняют существующие контракты.
- [ ] Все события первого среза пишутся в расширенный audit log без пароля и открытого OTP.
- [ ] SQL является расширяющим: новые таблицы/колонки/индексы/RLS/RPC/ограничения без удаления или переименования существующих полей и статусов.
- [ ] Поведенческие, SQL-contract, browser и отрицательные тесты покрывают роли, статус, checkbox, OTP boundaries, idempotency, stale bundle, чужой ресторан, публичный gate и обязательную миграцию существующих ресторанов без legacy-bypass.

### Intentional deferrals

- Email/SMS/WhatsApp API не подключаются; используется только явно помеченный временный `manual_code`.
- Полный редактор документов, PDF-файлы документов, reacceptance, data-correction workflow, внешние уведомления и массовые операции не входят в первый срез.
- PDF-подтверждение акцепта входит в отдельный срез 3, но первый срез сразу хранит все необходимые для него неизменяемые данные.
- Демонстрационные заказы и исключение их из комиссий/финансов входят в срез 4; до него ожидающий ресторан может просматривать настроенный каталог, но не создавать заказы.
- Существующая cookie-панель не связывается с юридическим акцептом и меняется только при отдельной необходимости.

## Data and migration safety

- Миграцию создать только через `supabase migration new <name>` после утверждения критериев.
- До применения к production получить проверяемый backup/restore point; текущий подключённый hosted project не является production `api.wayyaam.ru`.
- На локальной/изолированной базе сначала применить миграцию, выполнить тестовые запросы RLS/RPC и advisors, затем получить чистый migration artifact.
- Не применять migration и не деплоить Edge Functions в production в рамках локальной реализации без отдельного подтверждения и доступного recovery path.
- Не удалять старые документы, акцепты, релизы, assets или резервные копии.
