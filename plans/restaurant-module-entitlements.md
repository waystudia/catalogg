# Plan: Restaurant module entitlements

**Branch**: codex/pos-module-entitlements
**Status**: Awaiting acceptance-criteria approval

## Goal

Супер-админ выдаёт ресторану модульный тариф WayYaam POS, а кабинет ресторана получает единый серверный источник прав, не меняя существующие каталог, заказы и публичное оформление.

## Parent split

Полный POS-эпик разделён на независимо выпускаемые пользовательские возможности:

1. Супер-админ управляет тарифом и модулями конкретного ресторана.
2. Сотрудник ресторана видит только разрешённые разделы и понятное состояние истёкшей подписки.
3. Кассир собирает новый заказ из существующего каталога без склада.
4. Кассир оформляет POS-заказ через совместимый контур текущих заказов.
5. Повар управляет POS-заказами на кухонном экране.
6. Кладовщик ведёт остатки, приходы, расходы и инвентаризации.
7. Владелец связывает блюда с техкартами, после чего склад списывается при статусе «Готовится».
8. Администратор настраивает акции, скидки, промокоды и комбо.
9. Владелец видит POS-финансы и отчёты.

Этот план покрывает только первый пункт и серверный контракт, необходимый второму.

## Acceptance Criteria

- [ ] В «Подписки и платежи» супер-админ открывает «Модули ресторанов» и видит каждый ресторан, тариф, статус подписки, дату окончания и состояния POS, склада, техкарт, финансов, акций и лояльности.
- [ ] Супер-админ выбирает пакет «Базовый», «POS», «POS + Склад» или «Полный»; интерфейс показывает точный набор модулей пакета до сохранения.
- [ ] После сохранения и повторной загрузки страницы выбранный пакет, индивидуальные флаги и лимиты сотрудников, устройств, точек и складов остаются прежними.
- [ ] Ресторан без записи модулей получает безопасный профиль «Базовый»: все новые модули выключены; текущие страницы каталога и заказов работают без изменений.
- [ ] Только супер-админ может изменять модульные права; владелец/участник ресторана может прочитать права только своего каталога.
- [ ] Истёкшая, просроченная, отменённая или заблокированная подписка возвращает режим `read_only`; активная и пробная — `active`; данные не удаляются при смене режима.
- [ ] SQL-миграция является только расширяющей: новые таблицы, индексы, RLS и функции; существующие таблицы и данные не переписываются.
- [ ] Контрактные тесты подтверждают default-off, соответствие четырёх пакетов, вычисление режима подписки и RLS/SQL-инварианты.
- [ ] Обязательные проверки рабочего заказа, lint, typecheck и build остаются зелёными.

## Slice 1: Супер-админ сохраняет модульный пакет ресторана

**Value**: Супер-админ может безопасно подготовить доступ к POS для одного ресторана, не включая функционал глобально.

**Path**: «Подписки и платежи» → «Модули ресторанов» → выбор ресторана и пакета/флагов/лимитов → API → Supabase `restaurant_modules` → повторное чтение и отображение сохранённого состояния.

**Intentional deferrals**: Навигация ресторана, экран кассы, создание POS-заказов, складские операции и биллинг оплаты не входят в этот срез.

**Required implementation skills**: Перед production-кодом загрузить `tdd`, `testing`, `mutation-testing`, `refactoring`; SQL и типы реализовать через тестируемый доменный контракт.

**Acceptance criteria**: Все критерии общего раздела, кроме фактического показа POS-навигации ресторану; серверное чтение прав своего ресторана входит в срез.

**RED**: Сначала добавить падающие тесты пакетов/default-off/access-mode и SQL-контракт на расширяющую схему с RLS.

**GREEN**: Добавить минимальные типы/селекторы, расширяющую миграцию, API чтения/сохранения и страницу управления модулями в существующем разделе подписок.

**MUTATE**: Запустить mutation testing для чистых правил пакетов и режима доступа.

**KILL MUTANTS**: Усилить тесты на каждый флаг, граничную дату окончания, `trial`/`active` и все неактивные статусы.

**REFACTOR**: Оценить извлечение страницы из монолитного `PlatformAdminApp.tsx`; оставить composition root и существующие маршруты неизменными.

**Done when**: Критерии выполнены, проверки зелёные, mutation report представлен пользователю; коммит выполняется только после отдельного одобрения.

## Follow-up slice

После завершения этого плана отдельный план добавит лицензированную POS-оболочку в кабинет ресторана: скрытая навигация при `disabled`, рабочая при `active`, просмотр без операций при `read_only`.

## Pre-PR Quality Gate

1. Mutation testing для правил entitlement.
2. Refactoring assessment.
3. Тесты рабочего заказа из `catalogg-working-order`.
4. Полные lint, typecheck и build.
5. Ручная проверка страницы супер-админа на desktop и mobile.
